# 团队流程

Lead 与实现者如何推进一轮工作。这是流程手册（playbook）；每个 agent 都必须遵守的规则在 [AGENTS.md](../../AGENTS.md)。

## 一页说明模型

- 工作按**轮次（round）**进行：一个里程碑或需求，最终形成一个合并提交。
- **Lead** 负责计划、冻结契约、拥有共享文件、审查、验证和提交。**Implementer** 拥有模块、写代码、本地验证并汇报证据。
- 每一轮：**需求受理（Intake）→ 契约（Contracts）→ 启动（Kickoff）→ 并行工作（Parallel work）→ 集成（Integration）→ 交付（Delivery）→ 回顾（Retro）**。
- **任务板（task board）**是共享状态；**`docs/`** 是共享记忆；**验证证据**是“完成”的唯一定义。
- 默认并行度：2–3 名实现者，每人一个模块，写范围互不重叠。

## 1. 角色

**Lead**——计划者与集成者。

- 把一个请求变成带显式非目标的单个里程碑切片。
- 编写接口契约：签名、单位、所有权、错误行为、文件格式。
- 拥有共享文件（根 `CMakeLists.txt`、`tests/CMakeLists.txt`、`docs/`、`AGENTS.md`）以及所有提交。当实现者可以做时，不实现模块代码。
- 回答契约问题、重新划定范围、保持任务板与文档最新。
- 审查每个 diff，运行最终验证，向用户交付本轮成果。
- 升级需要用户决定的事项，而不是猜测。

**Implementer**——模块所有者。

- 写代码前阅读 `AGENTS.md`、文档和自己的任务。
- 用当前 revision 认领任务，并留在自己的写范围内。
- 保留私有构建目录，本地验证（构建、测试、演示命令）。
- 汇报改动文件、验证输出与不确定之处；立即提出阻塞。
- 从不提交、从不安装、从不编辑共享文件或同伴的模块。

**Peer reviewer**——可选，在 Lead 本人编写了改动或模块有风险时使用。检查清单与 Lead 审查相同；发现的问题交给所有者，而不是直接编辑。

## 1b. Shared state（共享状态）

- **任务板** —— 由 agent 运行时提供：用当前 `revision` 创建任务、认领/完成任务。任务有 id、subject、description（目标、写范围、契约、验收）、owner、status、`revision`、`blocked_by` 以及声明的写范围。如果运行时没有任务板，就在每轮使用一个受跟踪的 `docs/tasks/<milestone>.md`，字段相同。
- **新模块注册** —— 根与测试 `CMakeLists.txt` 维护显式的模块列表。Lead 添加一次新模块名；尚不存在的目录会被跳过。模块所有者从不编辑这些共享列表。
- **Git** —— 每轮一个合并提交，只由 Lead 制作。

## 2. Phase 0 — Intake（需求受理）

任何代码之前：

- 用一句话复述请求：目标、范围、非目标、成功标准。
- 检查约束：所需依赖（已批准？）、平台、确定性、可测试性。
- 列出只有用户能做的决定；尽早询问，在契约冻结之前。
- 只挑一个能在最后演示的里程碑切片。
- 识别有风险的部分（视觉输出、网络、解析边界情况）以及如何验证它们。
- 估算：模块数、可能的文件、并行拆分、预期规模。如果切片看起来大于一轮，就切小。

输出：给用户的简短计划，以及（被接受后）更新后的路线图条目。

## 3. Phase 1 — Plan and freeze contracts（计划并冻结契约）

把切片拆成 2–4 个任务。一个任务 = 一个模块（或一条薄的垂直路径）= 一个所有者。

任务描述模板：

```text
Goal: one sentence.
Write scope: the only paths the owner may modify.
Contract: public headers/types, units, ownership, error behavior, file formats.
Acceptance: exact commands that must pass and the expected observable result.
Dependencies: other tasks (blocked_by) or "none".
Rules: no commits, no installs, English files, private build directory.
```

Definition of Ready（就绪定义）——启动之前必须全部为真：

- 契约是显式的；没有单位或生命周期留给解释。
- 验收命令可运行且无歧义。
- 任何新依赖都有记录在 `docs/dependencies.md` 的用户批准。
- 写范围互不重叠；共享文件恰好有一个所有者（Lead）。
- 每个任务小到能在一个会话内完成；过大的任务要拆分。

## 4. Phase 2 — Kickoff（启动）

- 最多启动三名实现者。每个 prompt 自包含：仓库路径、要阅读的文档、任务 id、契约摘要、范围、构建命令、规则、汇报格式。
- 实现者用当前 revision 认领任务，然后先读后写。
- 阅读过程中发现的契约缺陷报告给 Lead；Lead 修正契约并向所有受影响的成员重新通告。

## 5. Phase 3 — Parallel work（并行工作）

Lead：

- 关注任务板并及时回答问题；从不让成员因阻塞而空转。
- 每次契约变更都一次性通知所有受影响的成员。
- 在轮次进行中把决定记录到正确的文档里。
- 回复集中在“改了什么 / 什么还不清楚”。
- 不开始实现已有所有者的模块；只做接线和共享文件。

Implementer：

- 留在写范围内；别处需要的改动变成一条消息，而不是一次编辑。
- 在自己的目录中构建；从不触碰其他成员的构建树。
- 尽早汇报阻塞和歧义，说明被什么阻塞、需要什么。
- 保持模块自包含并遵守模块边界。
- 不做顺手重构，没有契约变更就不添加新抽象。

检查点是轻量的：只在完成、遇到阻塞或 Lead 询问时汇报。

## 6. Phase 4 — Integration and verification（集成与验证）

Lead 从不只信一份报告。审查：

- 范围：只有声明过的文件被改动；实现者没有碰共享文件。
- 边界：没有层次违规、没有依赖环、渲染器中没有页面逻辑。
- 质量：MVP 规模、没有推测性抽象、没有隐藏未完成工作的 TODO、没有机器特定路径或版本、英语注释、格式干净。
- 测试：正常、边界和失败路径；确定性；无显示器或网络。

验证门，由 Lead 在合并并行工作后运行：

1. 用每个受支持的编译器组（GCC 和 Clang）做全新构建，警告视为错误。
2. 在每个全新构建上运行完整 `ctest` 套件。
3. 本轮的演示命令，检查其可观察输出（不只是退出码）。
4. 对任何需要硬件或显示器的内容（窗口、网络）做手动冒烟测试，并记录在报告中。
5. `git status` 中没有构建产物；没有多余文件。

缺陷作为后续任务或消息退回给所有者；Lead 不悄悄修补它不拥有的模块。只有接线和共享文件修复属于 Lead。

## 7. Phase 5 — Delivery（交付）

- 更新本轮改动过的文档：路线图状态、README 状态、行为变化时的架构或约定、依赖审批、待决问题、经验。
- 英语优先：先更新 `README.md`，再更新 `README.zh.md`，并让它们的状态行在同一轮中保持一致。
- 每轮做一个合并提交，用英语提交信息写出里程碑名称。
- 关闭任务；把它们留在任务板上作为本轮审计轨迹。
- 向用户汇报：交付了什么、验证证据、文档改了什么、剩余风险，以及提议的下一轮。请求接受或修正。

## 8. Phase 6 — Retrospective（回顾）

三个问题，简短回答，记录在经验日志中：

1. 什么有效、应该保留？
2. 什么造成了痛苦或浪费时间？
3. 流程手册、某个约定或 `AGENTS.md` 应该改什么？

只有持久的规则才进入 `AGENTS.md`；其余留在这里。尽可能把经验放进本轮同一个提交。清理过期的构建目录和多余文件。

## 9. Round types（轮次类型）

- **Feature / milestone**——默认：契约、并行模块、完整验证。
- **Bugfix**——先写失败的回归测试，修复，验证测试修复前失败、修复后通过；不扩大范围。
- **Refactor**——保持行为，现有测试必须保持绿色，一次一个模块；不要把重构混进功能轮次。
- **Spike / research**——有时间盒，不写生产代码，输出一份简短文档或决定；发现用于下一轮计划。
- **Docs round**——不写代码；验证链接、状态和检查清单仍与现实一致。

## 10. Collaboration conventions（协作约定）

- 每条路径一个所有者；共享文件恰好一个所有者，即 Lead。
- 契约优先，代码其次：单位、所有权、错误和格式在工作开始前决定。
- 不悄悄扩大范围；额外工作变成新任务或问题。
- 证据胜过声明：每份完成报告都包含所运行的命令及其输出。
- 隔离的构建目录；绝不在源码树或同伴的构建目录中构建。
- 确定性测试：单元测试不依赖显示器、网络、字体、locale 或时钟。
- 仓库文件用英语；面向用户的对话遵循用户自己的语言偏好；个人与机器特定的细节不进入仓库。
- 实现者不提交、不安装、不下载；依赖变更必须先获用户批准。
- 保持历史可读：每轮一个合并提交，而不是一串碎片。
- 文档边工作边更新，而不是最后重建。

## 11. Communication protocol（沟通协议）

- 阻塞消息：什么被阻塞、需要什么、期间可以继续什么。
- 契约问题：陈述歧义、提出默认方案、指出受影响的成员。
- 完成报告：改动的文件、验证证据、不确定之处、风险。
- 不做轮询循环；等待事件而不是反复询问。
- 团队内部消息可以使用最高效的语言（建议英语以保证精确）；与用户的对话遵循用户自己的语言偏好。
- 用户决定要升级，绝不臆造。

## 12. Anti-patterns（反模式）

- 为小事启动很多成员；协调多于工作。
- 模糊的契约（“让它能跑就行”）导致无声返工。
- 实现者编辑共享文件或彼此的模块。
- 没有全新构建和可观察输出就接受“测试通过”。
- 多个 agent 提交，或提交未验证的并行工作。
- 范围蔓延、推测性抽象、把重构夹带进功能。
- 文档漂移：代码已落地，文档还在描述之前的状态。
- 需要显示器、网络或已安装字体的测试。
- Lead 英勇地修一个模块，而不是把缺陷转给它的所有者。
- 重写已经发布的历史。

## 13. Lessons log（经验日志）

- M1：在契约中显式说明共享结构的单位；`PixelView.stride` 需要一次跨模块确认，而一份精确的契约本可以避免它。
- M1：CMake 模块自动包含消除了并行工作的主要共享文件争用点。
- M1：窗口行为无法 headless 单元测试；模块所有者加了一次性回读检查，Lead 用真实窗口冒烟测试加 PPM 像素验证收尾。
- M1：仓库根目录出现的散落目标文件来自临时编译；只在自己的构建目录中构建。
- M1：Lead 在合并并行工作后重新跑了全新的 GCC 与 Clang 构建（警告视为错误）和完整测试套件，然后做了一个合并提交。
- M2：Lead 必须在启动模块所有者之前更新根/`tests` CMake 中的共享模块列表；kickoff 时发现 net 模块不在那些列表里。
- M2：给一个用聚合初始化的结构体加字段会在 `-Wextra -Werror` 下触发 `-Wmissing-field-initializers`；调用方优先逐字段赋值，或使用写全每个字段的花括号初始化。
- M2：端到端 CLI 行为只用 CMake 就能测试——`file(WRITE)` fixture 加 `PASS_REGULAR_EXPRESSION`/`WILL_FAIL`——不需要测试框架或捕获 stdout。
- M2：非 2xx 的 HTTP 响应是成功的传输，所以 `--dump-body` 会打印错误页 body；导航语义要到后续里程碑才有。
- M3：启动前预先更新共享 CMake 模块列表（M2 的教训）完全消除了 kickoff 阻塞；两个串行任务（dom，然后 shell）不需要其他协调。
- M3：冻结契约之外的决策（逐字注释数据、空白路由、无隐含 head 路由）由所有者报告，并作为文档化的 MVP 限制写进路线图的已知限制列表，而不是被悄悄改掉。
- M3：解析器的健壮性检查（随机/畸形输入、深层嵌套、ASan/UBSan）成本很低，值得作为 dom 和 css 模块的习惯保留。
- M3：一个建立在 CMake 正则上的测试断言在信任它之前先用 `cmake -P` 验证过；断言本身也需要验证。
- M3：英语 `README.md` 的状态落后于 `README.zh.md`，因为一次脚本化文本替换悄悄什么都没做。验证自动化文档编辑（替换后 grep 新文本），并在交付前检查 README/README.zh 是否一致。
- M3 之后的审阅轮（两名只读审阅者，全新上下文，代码与文档，一轮）：发现一个真实 bug（`--size` 无上限）、两个契约/健壮性缺口（`file://` 忽略 body 大小上限、dump 缩进是二次复杂度）以及若干过期文档。每 2-3 个里程碑做一次低成本审阅是值得的；让审阅者保持只读，并把修复转给模块所有者。
- M4：先发布 css 公共头文件，让 style 模块能真正按契约并行编写；唯一的协调是“重试 configure 直到 css 目标存在”。
- M4：同样的 dump 缩进问题在新的 style dump 中再次出现，因此所有者立即套用了已有的上限模式；修复一类 bug 时，也要检查其他 dump。
- M4：队友的自报告指出了契约缺口（行内 `!important`、命名颜色取值、无上限的 style dump 缩进），由 Lead 决定接受或修复；保持这种上报习惯——它比一轮审阅更便宜。
- M5：按 M4 的教训，启动时就要求 layout 公共头文件作为显式检查点发布，让 shell/CLI 所有者能与布局实现并行开始；额外的协调只有一条简短的“header published”消息。
- M5：两项 Lead 侧的启动前准备工作——header-only 的 `tests/support/check.h` 加 `toy_test_support` 接口目标——把重复的基础设施决策从实现者手里拿走了，也完成了路线图 backlog 条目，而无需改动旧测试。
- M5：布局契约有六个真正模糊的边角情况（br 与 display、行尾空行、被拆分行内元素的 padding、纯空白节点、隐藏的 html、带待处理行内 padding 的适配检查）。把它们一次性列出并经过一轮批准，比在集成时发现行为分歧便宜得多。
- M5：由于盒 dump 是用户可见且冻结的，Lead 在契约中手工推导了端到端预期几何，layout 与 shell 两个所有者各自独立推导；第一次就完全一致。输出格式被冻结时，把算好的 golden 值写进契约。
- M5：深层嵌套安全从一开始就设计进去（迭代式布局、不做 DOM 递归、dump 有上限、10k div 回归测试），而不是靠审阅轮发现；完整的 31 个测试套件运行时间不到一秒。
- M6：header 检查点的模式第三次奏效——提前发布 `render::DisplayList` 让 `paint` 模块以及之后的 shell/CLI 切片都能按冻结契约并行推进。
- M6：Lead 对光栅化器的审阅发现了真实的健壮性 bug（超大的 CSS `font-size` 让字形迭代无界，并使源映射算术溢出）。它作为带复现步骤的小跟进任务退回模块所有者；修复前后的截图证明普通输出未变。从一开始就把渲染器当作对抗性输入代码对待。
- M6：确定性渲染器带来非常廉价的验收门——`cmp` 两个编译器的 PPM，再把一张截图转成 PNG 看一眼；这次没有发现问题，但字形或绘制顺序错误恰恰是断言容易漏掉、肉眼能发现的。
- M6：shell 所有者先从冻结的 `--dump-boxes` 输出推导像素测试几何，再写断言，因此端到端测试只在尚未实现的光栅化器上失败，而不是在布局分歧上。
- M6：无需额外工具就完成了窗口烟测——启动浏览器，在 `xwininfo -root -tree` 里找到它具体的 client window，再用 ImageMagick `import` 抓取（本机不需要 `xdotool`）；只抓 client window，不抓 root。
- M7：提前冻结全部五个公共头文件（net/layout/paint/platform/shell），让三个模块加 shell 会话能按显式
  契约并行编写；代价是 shell 波次落地前默认全量构建会在 `toy_shell` 里坏掉，所以每个 kickoff 提示都
  必须写明“只构建你自己的目标，全量构建预期会失败”。这句话消除了唯一可能的无效调试来源。
- M7：一个 headless 的 `shell::Browser` 会话类让链接、历史、滚动与标题都能不开窗口测试，窗口循环
  变成薄呈现层；`--screenshot` 走同一条路径，两条呈现路径不会漂移。
- M7：绘制改动时，用上一提交的 `git worktree` 做基线是很便宜的逐字节回归门：加入视口裁剪命令后，
  所有 dump 与滚动 0 截图都与基线 `cmp` 一致。
- M7：平台输入无法 headless 单测，所以平台所有者先在 `.tmp/` 写了一次性 X11 冒烟程序（标题回读、
  按键映射）；Lead 的真实窗口冒烟只需证明 shell 接线。
- M7：真实窗口冒烟需要的是 *client* window，而不是窗口管理器边框（两者都带标题）；用
  `xwininfo -root -tree` 找到它、`import -window` 抓取，再用只链 libX11 的小 XSendEvent 工具注入
  输入——不需要 `xdotool`，也没有新依赖。
- M7：把 fixture 的链接坐标硬编码自一次 `--dump-boxes` 运行（与 M6 相同做法）让导航测试保持
  headless 且快速；fixture 与坐标必须一起改动。
- M7：只读的子代理审计（解析字节、把每个字形打印成 ASCII art、与目标字符比对）在手写字形表里
  找出了 11 个真实的形状/对齐错误——既有像素测试全部漏掉，因为那些测试只渲染 `H`，而 `H` 在水平
